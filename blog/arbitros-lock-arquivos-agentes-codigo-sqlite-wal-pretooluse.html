1. O Problema da Sobrescrita Silenciosa em Enxames de Agentes

Executar um único agente de código é rápido; executar quatro ou oito subagentes especializados em paralelo em um monorepo é transformador — até o momento em que dois agentes editam o mesmo arquivo. Em uma árvore de trabalho compartilhada, cada agente raciocina sobre um snapshot independente e potencialmente defasado do disco dentro de sua janela de contexto.

Considere a clássica condição de corrida de atualização perdida (lost-update):

  1. Em t = 0s, o Agente A (Refatoração de API) lê src/router.py e inicia o raciocínio para aplicar um patch de 25 linhas.
  2. Em t = 1.8s, o Agente B (Middleware de Auth) lê src/router.py, conclui sua inferência antes e invoca Write ou Edit para inserir uma verificação de autenticação.
  3. Em t = 3.1s, o Agente A emite seu payload de Write calculado sobre o estado de t = 0s. O sistema de arquivos do SO sobrescreve o inode sem reclamar, apagando silenciosamente o middleware do Agente B com zero mensagens de erro.

Pedir aos agentes que se coordenem via linguagem natural ("edite apenas os arquivos designados no prompt") é probabilístico e colapsa imediatamente em arquivos barrel compartilhados, lockfiles, schemas de banco de dados ou imports transitivos. Não se resolve um risco de concorrência com engenharia de prompt; resolve-se com um árbitro determinístico de exclusão mútua na fronteira de execução da ferramenta.

Invariante Arquitetural: Toda chamada mutadora do sistema de arquivos (Write, Edit, MultiEdit) deve adquirir um lock atômico baseado em lease antes que a ferramenta execute. O Benni-OS/claude-code-swarm impõe essa garantia em menos de 1 milissegundo usando um árbitro local em SQLite3 WAL conectado ao evento nativo PreToolUse do Claude Code.

2. Leases Pessimistas vs. Otimistas e Expiração por TTL

Ao projetar controle de concorrência para agentes autônomos de código, a primeira decisão estrutural é escolher entre travamento otimista e pessimista.

  • Controle de Concorrência Otimista (OCC): Os agentes leem e geram edições livremente e comparam o hash SHA-256 ou mtime do arquivo apenas no momento da gravação. Se houver conflito, o agente perdedor descarta o patch e tenta novamente. Em sistemas baseados em LLM, o OCC é proibitivamente caro: um patch rejeitado desperdiça de 5 a 30 segundos de latência e milhares de tokens de saída.
  • Leases Pessimistas com TTL Limitado: Um agente precisa adquirir um lease exclusivo sobre o caminho canônico do arquivo antes de modificá-lo. Se outra sessão ativa detiver o lease, o hook PreToolUse falha rápido (< 1ms) e retorna um erro determinístico de conflito antes que o agente corrompa o estado ou queime mais turnos.

Por que Todo Lease Exige um TTL (Time-To-Live)

Em sistemas distribuídos, um lock sem prazo de expiração é um deadlock esperando para acontecer. Agentes de código são processos efêmeros: um subagente pode atingir timeout, ser encerrado por Ctrl+C, sofrer OOM ou disparar um circuit breaker FinOps no meio da tarefa. Se esse agente nunca alcançar PostToolUse ou SubagentStop para liberar o lock, o arquivo ficaria travado para sempre.

Por isso, todo lock no claude-code-swarm é um lease com tempo limitado (padrão ttl_seconds = 120). Cada registro armazena owner_session_id, fencing_token (um inteiro monotonicamente crescente), acquired_at e expires_at. Qualquer transação BEGIN IMMEDIATE subsequente remove atomicamente linhas expiradas (WHERE expires_at <= now) antes de avaliar a posse — entregando recuperação automática contra falhas sem daemons coletores em segundo plano.

3. Fluxo de Sequência: Interceptando Write/Edit no PreToolUse

O Claude Code invoca o PreToolUse de forma síncrona via JSON no stdin antes de executar qualquer ferramenta. Quando dois agentes paralelos miram o mesmo caminho canônico, o árbitro SQLite WAL serializa as requisições de lock de forma determinística:

sequenceDiagram autonumber participant A as Agente A (Sessão 101) participant H as Hook PreToolUse participant DB as Árbitro SQLite3 WAL participant B as Agente B (Sessão 204) A->>H: Propõe Edit(src/router.py) H->>DB: BEGIN IMMEDIATE; limpa expirados; UPSERT lease(src/router.py, owner=101, TTL=120s) DB-->>H: OK (fencing_token=42) H-->>A: Exit 0 (Permite Write/Edit) B->>H: Propõe Write(src/router.py) H->>DB: BEGIN IMMEDIATE; verifica dono de src/router.py DB-->>H: CONFLITO (retido por 101, expires_at > now) H-->>B: Exit 2 + stderr("LOCK_CONFLICT: retido pela sessão 101, tente em 15s") A->>H: PostToolUse / SubagentStop (libera lease 101) H->>DB: DELETE FROM file_leases WHERE path='...' AND owner='101' DB-->>H: Liberado

Observe duas propriedades críticas desse fluxo:

  1. Reentrância Idempotente: Se o Agente A já detém o lease de src/router.py e emite um segundo Edit no mesmo arquivo dentro da janela de TTL, o árbitro renova expires_at e permite a execução imediatamente.
  2. Backoff com Zero Tokens Extras: O Agente B recebe uma mensagem objetiva em stderr via código de saída 2, permitindo que ele pivote para um módulo livre ou aguarde a liberação no SubagentStop do Agente A.

4. Schema SQLite3 WAL Atômico e Implementação do Árbitro em Python

Arquivos .lock ingênuos no sistema de arquivos sofrem com condições de corrida TOCTOU (Time-of-Check to Time-of-Use) e bugs de limpeza entre plataformas. O SQLite3 em modo Write-Ahead Logging (WAL) oferece transações ACID, implantação em arquivo único sem daemon e contenção sub-milissegundo via busy_timeout.

Schema SQLite3 WAL

PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
PRAGMA busy_timeout = 5000;

CREATE TABLE IF NOT EXISTS file_leases (
    canonical_path  TEXT PRIMARY KEY,
    owner_id        TEXT NOT NULL,
    fencing_token   INTEGER NOT NULL,
    acquired_at     REAL NOT NULL,
    expires_at      REAL NOT NULL
);

CREATE TABLE IF NOT EXISTS lease_sequence (
    id              INTEGER PRIMARY KEY CHECK (id = 1),
    next_token      INTEGER NOT NULL DEFAULT 1
);

INSERT OR IGNORE INTO lease_sequence (id, next_token) VALUES (1, 1);
CREATE INDEX IF NOT EXISTS idx_leases_expires ON file_leases (expires_at);

Hook PreToolUse em Python e Árbitro Atômico de Leases

Abaixo está o árbitro atômico central usado pelo claude-code-swarm. Todo caminho é normalizado via os.path.realpath para que symlinks e caminhos relativos (./src/../src/router.py) apontem para exatamente a mesma chave de lock:

import json
import os
import sqlite3
import sys
import time
from pathlib import Path

DB_PATH = Path(".swarm/file_leases.db")
MUTATING_TOOLS = {"Write", "Edit", "MultiEdit"}
DEFAULT_TTL_SECONDS = 120.0


def init_db(conn: sqlite3.Connection) -> None:
    conn.execute("PRAGMA journal_mode = WAL;")
    conn.execute("PRAGMA synchronous = NORMAL;")
    conn.execute("PRAGMA busy_timeout = 5000;")
    conn.executescript(
        """
        CREATE TABLE IF NOT EXISTS file_leases (
            canonical_path TEXT PRIMARY KEY,
            owner_id TEXT NOT NULL,
            fencing_token INTEGER NOT NULL,
            acquired_at REAL NOT NULL,
            expires_at REAL NOT NULL
        );
        CREATE TABLE IF NOT EXISTS lease_sequence (
            id INTEGER PRIMARY KEY CHECK (id = 1),
            next_token INTEGER NOT NULL DEFAULT 1
        );
        INSERT OR IGNORE INTO lease_sequence (id, next_token) VALUES (1, 1);
        """
    )


def acquire_lease(
    db_path: Path, target_path: str, owner_id: str, ttl: float = DEFAULT_TTL_SECONDS
) -> tuple[bool, int, str]:
    canonical = os.path.realpath(target_path)
    now = time.time()
    expires_at = now + ttl
    db_path.parent.mkdir(parents=True, exist_ok=True)

    conn = sqlite3.connect(str(db_path), isolation_level=None, timeout=5.0)
    try:
        init_db(conn)
        conn.execute("BEGIN IMMEDIATE;")

        # 1. Remove leases expirados atomicamente (auto-recuperação pós-crash)
        conn.execute("DELETE FROM file_leases WHERE expires_at <= ?;", (now,))

        # 2. Verifica o detentor atual do lease ativo
        row = conn.execute(
            "SELECT owner_id, fencing_token, expires_at FROM file_leases WHERE canonical_path = ?;",
            (canonical,),
        ).fetchone()

        if row is not None and row[0] != owner_id:
            remaining = max(0.0, row[2] - now)
            conn.execute("ROLLBACK;")
            return (
                False,
                row[1],
                f"LOCK_CONFLICT: '{canonical}' is leased by session '{row[0]}' "
                f"(token={row[1]}, expires in {remaining:.1f}s).",
            )

        # 3. Emite fencing token monotônico e faz upsert do lease
        token = conn.execute(
            "UPDATE lease_sequence SET next_token = next_token + 1 WHERE id = 1 RETURNING next_token - 1;"
        ).fetchone()[0]

        conn.execute(
            """
            INSERT INTO file_leases (canonical_path, owner_id, fencing_token, acquired_at, expires_at)
            VALUES (?, ?, ?, ?, ?)
            ON CONFLICT(canonical_path) DO UPDATE SET
                owner_id = excluded.owner_id,
                fencing_token = excluded.fencing_token,
                acquired_at = excluded.acquired_at,
                expires_at = excluded.expires_at;
            """,
            (canonical, owner_id, token, now, expires_at),
        )
        conn.execute("COMMIT;")
        return True, token, f"LOCK_ACQUIRED: '{canonical}' (token={token})."
    except Exception:
        conn.execute("ROLLBACK;")
        raise
    finally:
        conn.close()


def main() -> None:
    payload = json.load(sys.stdin)
    tool_name = payload.get("tool_name", "")
    if tool_name not in MUTATING_TOOLS:
        sys.exit(0)

    tool_input = payload.get("tool_input", {})
    file_path = tool_input.get("file_path") or tool_input.get("path")
    if not file_path:
        sys.exit(0)

    owner_id = payload.get("session_id", "default-agent")
    acquired, _, message = acquire_lease(DB_PATH, file_path, owner_id)
    if not acquired:
        sys.stderr.write(message + "\n")
        sys.exit(2)

    sys.exit(0)


if __name__ == "__main__":
    main()

5. Comparativo de Latência e Arquitetura de Concorrência

Por que escolher SQLite3 WAL + PreToolUse em vez de Git worktrees, Redis ou arquivos .lock tradicionais? Veja como as abordagens se comportam sob carga de enxames paralelos:

Estratégia de Arbitragem Latência de Aquisição Recuperação pós-Crash (TTL) Infra Externa Segurança contra Race Conditions
Coordenação via Prompt (CLAUDE.md) 0 ms (probabilística) N/A Nenhuma Insegura (sobrescritas silenciosas em arquivos comuns)
Arquivos .lock Ingênuos (open(..., 'x')) 0.2 – 1.5 ms Manual / mtime frágil Nenhuma Parcial (TOCTOU na limpeza e sem fencing token)
Git Worktrees por Agente 150 – 800 ms (checkout) Vinculada ao processo Git CLI Alta (árvores isoladas, mas adia conflitos para o merge)
Lock Distribuído Redis (Redlock) 1.5 – 5.0 ms (TCP/localhost) TTL nativo via PX Daemon Redis Alta (exige subir e monitorar servidor Redis)
claude-code-swarm SQLite3 WAL 0.3 – 0.9 ms (in-process) Remoção atômica via TTL em BEGIN IMMEDIATE Zero (stdlib sqlite3) Serialização ACID + Fencing Tokens Monotônicos

Na prática, o SQLite3 WAL atinge o ponto ótimo de engenharia para enxames locais de agentes de código: aquisição de lock sub-milissegundo, zero daemons externos, serialização ACID entre processos independentes do sistema operacional e recuperação determinística contra quedas via TTL.

Perguntas Frequentes

Por que agentes de código paralelos sobrescrevem silenciosamente os arquivos uns dos outros?
Quando múltiplos agentes compartilham um workspace, seus ciclos Read-Think-Write se sobrepõem. O Agente A lê um arquivo em t=0, o Agente B grava um patch em t=2, e o Agente A emite um Write completo ou Edit obsoleto em t=3 baseado no estado antigo — apagando silenciosamente as alterações do Agente B sem gerar nenhum erro no sistema operacional.
Por que usar leases pessimistas com TTL em vez de controle de concorrência otimista para agentes de código?
O controle otimista detecta conflitos apenas depois que o agente já queimou tokens de LLM e tempo de inferência gerando o patch. Leases pessimistas falham rápido no hook PreToolUse antes da execução, enquanto um Time-To-Live (TTL) limitado garante que um agente encerrado com SIGKILL nunca deixe o arquivo em deadlock permanente.
Como o SQLite3 WAL garante aquisição atômica de locks entre processos de hook concorrentes?
Ao ativar PRAGMA journal_mode=WAL e iniciar transações com BEGIN IMMEDIATE, o SQLite serializa todas as transações de escrita entre processos independentes do SO em nível de biblioteca C. Leases expirados são removidos e novos leases são inseridos dentro de uma única transação atômica, eliminando condições de corrida TOCTOU.
Como o Benni-OS/claude-code-swarm aplica locks de arquivos no Claude Code?
O claude-code-swarm registra um hook PreToolUse que intercepta chamadas Write, Edit e MultiEdit, normaliza o caminho alvo via realpath e consulta o árbitro SQLite WAL. Se outro agente ativo detiver um lease válido, o hook encerra com código de saída 2 e retorna uma mensagem estruturada em stderr para que o agente bloqueado recue ou aguarde.
