Evals de CI/CD para Claude Code: Benchmarks de CLAUDE.md, Ferramentas MCP e Regressões de Subagentes Antes do Merge

Por que editar CLAUDE.md, .claude/commands/ ou schemas de ferramentas MCP sem evals determinísticas em CI/CD degrada silenciosamente a confiabilidade do agente — e como o Benni-OS/claude-code-eval executa evals de trajetória offline a $0.00, mede pass@k e eficiência de tokens, aplica portões --min-pass-rate no GitHub Actions e emite recibos SHA-256.

1. O Problema da Regressão Silenciosa: Prompts São Código de Produção

Equipes de engenharia tratam módulos Python e TypeScript com rigor absoluto — testes unitários, checagem estática de tipos e status checks obrigatórios no CI antes de qualquer merge. Ainda assim, os arquivos que realmente governam como o Claude Code raciocina, escolhe ferramentas e delega para subagentes — CLAUDE.md, .claude/commands/ e schemas JSON de servidores MCP — chegam à main sem nenhuma verificação automatizada.

Quando você ajusta uma regra no CLAUDE.md ou renomeia um parâmetro na descrição de uma ferramenta MCP, o CI tradicional passa 100% verde enquanto a confiabilidade do agente colapsa silenciosamente em quatro modos de falha:

  • Sobrescrita de Instruções e Drift de Política: Adicionar uma diretiva de "seja conciso" ou uma nova convenção de repositório acaba sobrescrevendo uma restrição de segurança anterior, fazendo o agente pular a verificação de testes ou ignorar hooks de pré-commit.
  • Confusão na Seleção de Ferramentas MCP: Renomear um campo MCP ou expandir uma docstring faz o Claude Code desviar chamadas para o Bash em vez do servidor MCP estruturado, contornando guardrails determinísticos.
  • Quebra de Handoff entre Subagentes: Atualizar um slash command em .claude/commands/ altera o brief estruturado enviado aos subagentes, descartando contexto obrigatório ou schemas de saída.
  • Inflação de Tokens e Queda de Eficiência: Um acréscimo inocente de 400 tokens no CLAUDE.md ou um schema MCP verboso infla o prompt cache de cada turno e dispara loops desnecessários de ferramentas — dobrando o gasto de API sem alterar uma única linha do código da aplicação.
Princípio de Engenharia Central: Se algo governa o comportamento do agente, precisa passar por benchmark em cada pull request. O Benni-OS/claude-code-eval traz testes determinísticos de regressão em CI/CD para CLAUDE.md, slash commands, schemas de ferramentas MCP e trajetórias de subagentes — a $0.00 por execução de PR.

2. Arquitetura: Evals de Trajetória Offline a $0.00 e Portões de CI

Executar chamadas reais de LLM em todo pull request é lento, não determinístico e caro. O claude-code-eval separa a verificação determinística de trajetórias offline da amostragem opcional em modelo vivo, usando fixtures gravadas em JSONL e um harness local de simulação de MCP/ferramentas para validar cada PR em segundos:

flowchart TD PR["PR Altera CLAUDE.md / .claude/commands / Schema MCP"] -->|"Gatilho GitHub Actions"| E["Runner claude-code-eval"] E -->|"Carregar Fixtures JSONL"| R["Replay Offline de Trajetória $0.00<br/>(Ordem de Tools, Schema, Diffs)"] R -->|"Calcular Métricas"| M["pass@k + Delta de Eficiência de Tokens"] M -->|"pass@1 < --min-pass-rate"| F["Exit 1: Bloquear Merge no CI"] M -->|"pass@1 >= --min-pass-rate"| S["Gerar Recibo Canônico SHA-256"] S -->|"Arquivar Artefato"| G["PR Liberado para Merge na main"]

Em vez de adivinhar se uma edição de prompt melhorou ou quebrou seu fluxo, o runner de CI avalia cada fixture de trajetória contra invariantes rígidos: sequência esperada de chamadas de ferramentas, schemas válidos de argumentos MCP, padrões de comando proibidos e tetos de orçamento de tokens.

3. Os Quatro Primitivos Centrais do claude-code-eval

1. Replay Offline de Trajetórias a $0.00

Cada suíte de benchmark vive como fixtures versionadas de trajetória em JSONL sob evals/suites/. Durante o replay offline, o claude-code-eval injeta seu CLAUDE.md atualizado, slash commands e definições de ferramentas MCP em um harness local determinístico. Ele valida bindings de schema, precedência de regras, padrões proibidos e asserções de replay sem nenhuma chamada de rede externa — custando literalmente $0.00 por execução no CI.

2. Pontuação pass@k e Eficiência de Tokens

Anedotas de uma única execução escondem instabilidade. Ao rodar suítes estocásticas ou multi-seed, o claude-code-eval calcula pass@1 e pass@k ao longo de N tentativas junto com uma Razão de Eficiência de Tokens (comparando deltas de tokens de entrada/saída contra a baseline da main). Um PR que mantém a acurácia mas queima 35% mais tokens é sinalizado imediatamente antes do merge.

3. Portões de CI com --min-pass-rate

No GitHub Actions, o claude-code-eval atua como um status check rígido. Passar --min-pass-rate 0.95 e --max-token-regression 1.15 garante que nenhuma alteração em prompt, schema MCP ou subagente seja mesclada se a confiabilidade cair abaixo de 95% ou a sobrecarga de tokens passar de 15%.

4. Recibos Criptográficos de Avaliação SHA-256

Passar no CI deve deixar uma trilha imutável de auditoria. Toda execução aprovada grava um recibo JSON canônico (eval-receipt.json) contendo o SHA do commit, hashes SHA-256 do CLAUDE.md e dos schemas MCP, pontuações pass@k por suíte, métricas de eficiência de tokens e um digest principal receipt_sha256.

4. Configurando o claude-code-eval no GitHub Actions

Adicione um workflow dedicado em .github/workflows/claude-eval.yml para que todo PR que toque arquivos de configuração do agente execute automaticamente o portão offline de benchmark:

name: Claude Code Eval Gate

on:
  pull_request:
    paths:
      - "CLAUDE.md"
      - ".claude/**"
      - "mcp/**"
      - "evals/**"

jobs:
  offline-trajectory-eval:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"

      - name: Instalar claude-code-eval
        run: pip install claude-code-eval

      - name: Rodar Suíte Offline $0.00 e Aplicar Portão
        run: |
          claude-code-eval run \
            --suite evals/suites/core-workflows.jsonl \
            --mode offline \
            --k 3 \
            --min-pass-rate 0.95 \
            --max-token-regression 1.15 \
            --receipt-out artifacts/eval-receipt.json

      - name: Enviar Recibo de Avaliação SHA-256
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: claude-eval-receipt
          path: artifacts/eval-receipt.json

5. Por Dentro do Avaliador: pass@k, Eficiência de Tokens e Recibos SHA-256

Abaixo está a lógica determinística central de pontuação e emissão de recibos em Python. A partir dos resultados das trajetórias, ela calcula o estimador não viesado de pass@k, valida o limiar --min-pass-rate, verifica a eficiência de tokens frente à baseline e sela o resultado com um digest SHA-256 canônico:

import hashlib
import json
import math
import sys
from pathlib import Path


def compute_pass_at_k(n: int, c: int, k: int) -> float:
    """Estimador não viesado para pass@k dados n experimentos e c aprovações."""
    if n - c < k:
        return 1.0
    return 1.0 - math.comb(n - c, k) / math.comb(n, k)


def evaluate_suite_and_emit_receipt(
    results: list[dict],
    config_paths: list[Path],
    k: int = 3,
    min_pass_rate: float = 0.95,
    receipt_path: Path = Path("artifacts/eval-receipt.json"),
) -> int:
    total_cases = len(results)
    passed_cases = sum(1 for r in results if r["passed"])
    pass_rate = passed_cases / total_cases if total_cases else 0.0

    pass_at_k_scores = [
        compute_pass_at_k(r["n_trials"], r["n_passed"], k) for r in results
    ]
    mean_pass_at_k = sum(pass_at_k_scores) / len(pass_at_k_scores) if pass_at_k_scores else 0.0

    total_tokens = sum(r["tokens_used"] for r in results)
    baseline_tokens = sum(r["baseline_tokens"] for r in results)
    token_ratio = total_tokens / baseline_tokens if baseline_tokens else 1.0

    input_hashes = {
        str(p): hashlib.sha256(p.read_bytes()).hexdigest()
        for p in sorted(config_paths)
        if p.exists()
    }

    payload = {
        "mode": "offline",
        "cost_usd": 0.00,
        "total_cases": total_cases,
        "passed_cases": passed_cases,
        "pass_rate": round(pass_rate, 4),
        f"pass@{k}": round(mean_pass_at_k, 4),
        "token_efficiency_ratio": round(token_ratio, 4),
        "input_hashes": input_hashes,
        "gate_passed": pass_rate >= min_pass_rate,
    }

    canonical = json.dumps(payload, sort_keys=True, separators=(",", ":")).encode("utf-8")
    payload["receipt_sha256"] = hashlib.sha256(canonical).hexdigest()

    receipt_path.parent.mkdir(parents=True, exist_ok=True)
    receipt_path.write_text(json.dumps(payload, indent=2) + "\n", encoding="utf-8")

    return 0 if payload["gate_passed"] else 1


if __name__ == "__main__":
    sample_results = [
        {"id": "mcp-schema-route", "n_trials": 3, "n_passed": 3, "passed": True, "tokens_used": 1420, "baseline_tokens": 1500},
        {"id": "subagent-brief-gate", "n_trials": 3, "n_passed": 3, "passed": True, "tokens_used": 1890, "baseline_tokens": 1950},
    ]
    exit_code = evaluate_suite_and_emit_receipt(
        sample_results,
        [Path("CLAUDE.md")],
    )
    sys.exit(exit_code)

Perguntas Frequentes

Por que edições em CLAUDE.md ou schemas MCP quebram o Claude Code silenciosamente?
Regras do CLAUDE.md, workflows em .claude/commands/ e schemas JSON de ferramentas MCP funcionam como código executável do plano de controle do seu agente. Testes unitários e linters tradicionais não analisam instruções de prompt nem descrições de ferramentas, fazendo com que conflitos sutis de redação ou parâmetros renomeados causem desvio de escolha de ferramenta, pulos de portões de segurança ou inflação de 2× nos tokens em produção.
Como o claude-code-eval executa avaliações de trajetória offline a $0.00?
O claude-code-eval grava e reproduz fixtures determinísticas de trajetória em JSONL — capturando estado de prompt, sequências de chamadas de ferramentas, payloads MCP e diffs esperados no repositório — usando um runtime simulado local. No CI, ele valida conformidade de regras, ordenação de chamadas, invariantes de schema e eficiência de tokens sem realizar chamadas reais à API de LLM, mantendo o custo por PR em $0.00.
O que pass@k e --min-pass-rate medem no CI/CD?
pass@k mede a probabilidade de que pelo menos uma de k trajetórias amostradas do agente satisfaça todas as asserções determinísticas (testes passando, sequência esperada de ferramentas e teto de orçamento). Configurar --min-pass-rate 0.95 no GitHub Actions bloqueia qualquer pull request que reduza a confiabilidade do agente abaixo de 95%.
Por que o claude-code-eval emite um recibo de avaliação SHA-256?
Cada execução de CI gera um recibo JSON canônico contendo o SHA do commit Git, hashes das entradas CLAUDE.md e schemas MCP, métricas de pass@k, delta de eficiência de tokens e um digest SHA-256 determinístico. As equipes podem arquivar ou verificar recibos para comprovar que uma alteração de prompt ou MCP mesclada passou exatamente pelo portão de avaliação.
